# M0-001 · Should ggclusteroutline be built?

**Recommendation — stop standalone development at M0.** Existing R tools already draw the three useful kinds of guide in our examples. A base convex hull gives an all-observation envelope, ggforce gives a device-aware mark, and ggdensity gives a representative region that can split into islands. A saved vertex table already handles repeated plots. The unresolved requirement is automatic handling of holes, islands and outliers while presenting an unambiguous meaning to the reader. The experiments did not establish a safe universal default or a practical advantage for a new algorithm.

A thin wrapper remains a reasonable **alternative** if the scientist values a one-line, reusable all-observation envelope with explicit point/segment fallbacks enough to maintain a package. That narrower product would bridge unknown same-label islands. Its proposed contract and acceptance tests are ready for a separate GO. A fresh geometry engine has the weakest case.

## The scientist's visual decision

Start with the **separated islands** and **annulus**. Decide whether a reader should see an enclosure of every observed point or the estimated region where most observations lie. Then look at the outlier row and ask whether omitting an isolated point from the guide is acceptable when that point remains visible. The [visual decision record](design_evidence/M0-001.md) summarizes the four alternatives and leaves the scientist’s selection open. A Leiden label specifies membership on a graph. These shapes describe locations in a 2D projection and do not estimate biological borders.

- [Four-method comparison and robustness measurements](research/visual/README.md). Includes seeded fixtures, rendering settings, edge cases and thinning.
- [Nine additional shape comparisons](research/stress/README.md). Each row uses identical points, line settings for the two unpadded hulls, colours and axes across alternatives.

## What the benchmarks measured

The 95% HDR left the centre of the annulus empty while enclosing all 180 observed ring points. On the balanced two-island fixture it formed **one closed contour** covering 199/200 points, including the midpoint. The same topology persisted after removing 10% of observations once. On the separate unequal-density fixture the 90% contour split in two. Both the input and the probability level differ between these fixtures. Increasing the grid domain also mattered: at the narrower extent, the balanced-island contour intersected the grid boundary and produced open paths. Coverage from such paths is undefined without an explicit boundary convention. [Topology and removal measurements](research/visual/output/region_metrics.csv) · [independent SVG counts and domain check](research/review/README.md)

For 100,000 points in 100 groups on the Apple M5, median build + gtable + PNG draw took approximately **0.37 s for ggforce** and **2.0 s for ggdensity** with one requested 95% HDR level (three runs). The SVG exports contained 5,322 and 3,653 outline vertices, respectively. Fresh-process peak memory was approximately 289 and 314 MiB, including a subsequent SVG export and parse. The timings include the point layer. They apply to these settings and do not rank the quality of the regions. At one million points in 1,000 groups, only the base convex reference was measured. Its standalone geometry step took about 0.2 s and its complete PNG export about 2 s. The reference export rebuilds the plot, so adding its separate build time would double-count work. [Raw timing and memory records](research/scaling/results/)

The singleton HDR returned no contour with a computation warning; the oblique two-point example produced layer output. Distinct coordinate values along each axis affect KDE feasibility. A successful export alone can hide an empty layer, and finite output from two points is insufficient to justify a density-region interpretation. [Degenerate and missing-input checks](research/visual/output/degenerate_render_results.csv)

## Checks and limits

The updated [product proposal](specs/PRODUCT_SPEC.md) and [acceptance criteria](specs/ACCEPTANCE.md) define the smallest optional M1, including finite input, duplicate/degenerate handling, coverage, facet identity, cache invalidation and relative performance gates. No production implementation exists to validate against those gates. The test data cover geometric stress cases and an openly licensed real scatterplot. They do not establish acceptable results on a scientist-selected UMAP, long-term maintenance, cross-platform performance or a biological interpretation. M0 measured no cache implementation, downstream user effort or package demand.

**Approval requested — NO-GO M1** to retain the audit and use existing layers. An explicit **GO M1 — thin all-observation wrapper** instead authorizes only the bounded R implementation described in the specification. Automatic component discovery, density-mode development, releases and later milestones require separate decisions.
